# Contributing

sealr is an admission boundary, so the contribution process is part of the security posture. This page records the change-control rules the project holds itself to; they apply to the maintainer exactly as they apply to an external contributor.

## Getting started

The repository pins Rust 1.98.0 in `rust-toolchain.toml`; rustup selects it automatically.

```text
git clone https://github.com/blisspixel/sealr.git
cd sealr
cargo test --locked --workspace
```

Security reports never go through public issues or pull requests. Use [SECURITY.md](SECURITY.md).

## What the trusted computing base is

The TCB is the runtime code of the `sealr` crate — everything under `crates/sealr/src` that ships in the library. The CLI, the workspace tools, the fuzz targets, dev-dependencies, and test code are outside it. The committed [TCB report](docs/tcb-report.md) measures its size, `unsafe` surface, FFI boundary, runtime dependency graph, and panic sites; `scripts/verify_tcb_report.ps1` fails CI-style when the committed report drifts from the tree.

## Pull-request discipline for TCB changes

- **Size.** A pull request that changes TCB code should stay between roughly 300 and 800 changed lines of hand-written source. A change that cannot fit is split into dependency-ordered increments, each independently green. Mechanical surfaces — pinned conformance vectors, generated license bundles, fixture corpora, lockfile updates, and regenerated reports — are exempt from the count but must be separated from semantic changes so a reviewer never scrolls generated bytes to find a meaning change.
- **Review.** A TCB change requires review by someone other than its author before merge. The project currently has one maintainer, so this requirement is not yet satisfiable for maintainer changes; it is tracked as an open 1.0 gate in the [near-term plan](docs/near-term.md) rather than silently waived, and external review of the frozen surfaces is scoped there.
- **Report.** A TCB change regenerates `docs/tcb-report.md` in the same pull request (`pwsh -NoLogo -NoProfile -File scripts/generate_tcb_report.ps1`), so the measured deltas are visible to the reviewer next to the code that caused them.
- **Gates.** Every pull request passes the required CI check. Locally that means at minimum `cargo test --locked --workspace`, `cargo clippy --locked --workspace --all-targets` with warnings denied, `cargo fmt --check`, and the `scripts/verify_*.ps1` gates a change touches.

## Identity and evidence discipline

- Changing interpreted meaning, an identity encoding, or a denial classification requires a new versioned profile, policy, or schema identifier. Existing identifiers, digests, and layout labels are immutable historical contracts.
- Published measurement reports (the wheel-compatibility inventories, release notes, conformance manifests) are immutable evidence. A new measurement produces a new versioned report; it never edits an old one.
- Findings are typed and registered. A new failure mode gets a registered finding code and documentation, not a stringly-typed one-off.

## Dependency rule

New runtime dependencies require a written capability need and go through the gates in the [format support architecture](docs/format-support.md) and [codec dependency gates](docs/codec-dependency-gates.md). An existing reviewed dependency or a zero-dependency implementation is preferred. Unknown structure fails closed instead of pulling in a parser.

## Scope discipline

Parser breadth is currently frozen; see [What comes next](README.md#what-comes-next). A pull request adding a new archive format, however clean, is out of scope until the usefulness, compatibility, and review milestones land. Hostile fixtures, corpus evidence, documentation accuracy, and consumer integrations are in scope and welcome.
