# sealr 0.1.0-alpha.12

This twelfth development preview turns Sealr's verified archive decision into a more usable handoff. It ships byte-exact canonical evidence, a separately implemented verifier inside every native archive, a repository-owned PyPA conformance path, caller-authored validated policy files, and explicit inspect and materialize commands. It also releases the seven format selections completed after Alpha.11, bringing the explicit container and codec selection count to twelve while keeping ZIP32 as the unchanged compatibility default.

Alpha.12 remains a preview. It is useful for evaluation, integration work, and adversarial testing, but it is not ready to protect a production host from arbitrary hostile archives. Evidence is unsigned, the verifier cannot authenticate the archive containing it, the authenticated Linux worker remains ZIP32-only, no independently maintained project has adopted Sealr as authority, and no external security audit has completed.

## Downloadable evidence handoff

- Every Linux, macOS, and Windows native archive contains `sealr-identity-verifier` or its `.exe` form beside the `sealr` CLI. The verifier has no dependency on the Sealr crate and is not a separate release asset.
- Release archives still consist of exactly three target archives plus `SHA256SUMS`. GitHub build provenance binds each archive to this tag and release workflow.
- Required package checks use only the extracted executables. The extracted CLI produces admitted and coherent rejected canonical evidence; the extracted verifier checks each pair against the observed source and refuses view, receipt, source, and pair-substitution mutations.
- The verifier exposes explicit help, version, success, verification-failure, and usage-error contracts. Each evidence document is read from one open handle with a 16 MiB limit plus one detection byte, while source hashing streams through a fixed 64 KiB buffer.
- Users must verify `SHA256SUMS` and GitHub build provenance before trusting either executable. Shipping producer and verifier together provides implementation-independent evidence checking, not supply-chain independence.

## Canonical evidence and attestation input

- `Outcome::canonical_evidence()` and CLI `--canonical` produce exact RFC 8785 `sealr.view.v2` and `sealr.receipt.v3` bytes. The emitted view bytes reproduce the receipt's `view_digest`, and the receipt bytes have their own externally nameable SHA-256 digest.
- The independent verifier checks canonical bytes, pair bindings, the optional observed-source digest, every registered interpretation profile, known default-policy identities, outcome and effect consistency, and the format-neutral content root.
- Five committed evidence cases cover admitted inspection, committed materialization, structural rejection, unavailable source, and failed effect. Representative hostile mutations exercise shared claims and digest bindings.
- The verifier does not parse or decompress the archive, execute codecs, reconstruct the format-specific live layout root, prove SHA-256, authenticate a signer, or turn unsigned evidence into an attestation. Exit `0` means verification completed, including for coherent rejection evidence; consumers must inspect the evidence verdict.
- The non-published `sealr-attest` tool builds an unsigned in-toto Statement v1 from verified receipt v3 bytes and the actual source. Signing remains delegated to external DSSE or Sigstore tooling, so no signature implementation enters Sealr's trusted computing base.

## Repository-owned downstream conformance path

- The isolated packaged PyPA conformance kit compiles only against Cargo's extracted `sealr` package and drives exact `installer` 1.0.1 from bounded `VerifiedArchive` reads.
- It independently verifies canonical evidence, deletes the source before Python starts, denies every later `.whl` open, stages only verified member blobs, installs into five distinct roots, and independently audits every output into the realization identity.
- The kit covers a controlled semantic fixture and the real hash-pinned installer wheel. Lying `RECORD`, traversal, descriptor tampering, and staged-member tampering are denied before effects.
- The `wheel_admission` and `same_digest_different_tree` examples make the capability rule executable. The latter proves that one digest does not imply one install plan when outer artifact identity changes.
- Wheel support now includes Core Metadata 2.1 through 2.6. The predecessor-bound v4 and v5 inventories expand measurement to 64 and then 300 pinned artifacts, with every denial investigated rather than summarized as an acceptance percentage.
- Verified 1,024-byte prefix reads classify large wheel script members without releasing bytes before full size, CRC32, and SHA-256 verification. This admits the measured uv and ruff native-script shape while keeping exact launcher rewriting and the 16 MiB aggregate inspection bound.
- The final `python-wheel.v1` consumer profile digest is `2fd5f81e38b6ad483fa0e998f665cc466a9bd9816382299f4a64a0202f4a91bb`. The measured v5 corpus contains no Core Metadata 2.6 artifact, so that accepted specification version remains fixture-backed rather than population evidence.

This is strong repository-owned mechanism and evidence. It is not external adoption. The packaged kit is limited to Linux POSIX, no bytecode, no overwrite, 16 MiB per staged member, and 64 MiB total. The usefulness milestone remains open until a separately maintained publisher, registry, build backend, or installer treats the verified capability and evidence as authoritative and never reopens the source archive.

## Seven newly released explicit profiles

Alpha.12 releases seven selections that were not present in Alpha.11. None widens, aliases, retries, or falls back from another profile.

- `tar-gnu-longname` is a restricted raw old-GNU language under policy v6. It accepts one exact `L` path carrier for the immediately following member and denies long links, sparse files, base-256 numbers, mixed PAX state, and recovery behavior. Its layout identity is `sealrTreeV6`.
- `tar-gzip-pax` and `tar-gzip-gnu-longname` compose the frozen RFC 1952 wrapper separately with the restricted PAX and GNU languages under policy v7. Their layout identities are `sealrTreeV7` and `sealrTreeV8`.
- `tar-zstd-ustar` is the first Gate B codec promotion under policy v8 and `sealrTreeV9`. It uses exact `ruzstd` and `twox-hash` dependencies, rejects skippable and concatenated frames, caps the frame window at 8 MiB, and verifies the decoded TAR independently.
- `tar-xz-ustar` is the second Gate B codec promotion under policy v9 and `sealrTreeV10`. It uses `lzma-rust2` with a closed single-stream XZ language, an 8 MiB dictionary ceiling, exact padding, and independent check verification.
- `tar-bzip2-ustar` is the third Gate B codec promotion under policy v10 and `sealrTreeV11`. It uses `bzip2` over audited pure-Rust `libbz2-rs-sys`, binds bit-granular block evidence, and caps both work and decoded output.
- `7z-copy` is the first Gate C container step under policy v11 and `sealrTreeV12`. It accepts one raw-header, single-volume, Copy-only 7z language with exact CRC and dense-covering checks. Packed headers and LZMA or LZMA2 members remain unsupported.

Every profile publishes a distinct format-specific layout root while preserving the shared `sealrTreeV1` content identity after complete verification. Copy-only 7z provides the first committed cross-container content-root parity with the portable TAR family. All seven profiles run in process and are refused by the authenticated worker without fallback.

## CLI, policy, and API surface

- `sealr inspect <ARCHIVE>` and `sealr materialize <ARCHIVE> --dest <DEST>` are explicit aliases of the existing pipeline. The compatibility `sealr <ARCHIVE>` and `apply()` paths remain unchanged.
- `--view <NEW_FILE>` and `--receipt <NEW_FILE>` capture exact evidence without changing semantic exit status. `--canonical` requires both destinations and writes the RFC 8785 lineage without presentation output.
- `--policy <FILE>` accepts strict `PolicyDocument` JSON and constructs a proof-carrying `ValidatedPolicy` before archive evaluation. Unknown fields, schemas, values, and unsafe numeric caps fail before source access.
- All eleven default policies round-trip through the validated document form with unchanged bytes and digests. Caller policy identity is bound into the receipt.
- The public API contract now has a compile-time path and signature fixture. `Request` remains a permanently exhaustive three-field structure; future operation inputs arrive through `ApplyOptions`. `Policy` is non-exhaustive, and `RealizationIdentityError` exposes accessors instead of public fields.
- These are deliberate pre-freeze preview changes. Public API stability is not yet promised, and the exact compatibility check retains seven known warnings against the authenticated Alpha.11 baseline until Alpha.12 becomes the next published baseline.

## Assurance and hardening

- ClusterFuzzLite runs bounded AddressSanitizer discovery on relevant pull requests. Release promotion separately requires fourteen exact-commit on-demand fuzz jobs covering the worker protocol, semantic records, every TAR dialect and wrapper, strict ZIP64, all three promoted codecs, and Copy-only 7z.
- A regenerable trusted-computing-base report measures runtime lines, unsafe and FFI sites, panic sites, target dependency graphs, and cfg-gated modules. CI rejects report drift.
- Scheduled compiler-accurate `cargo-semver-checks` discovery authenticates the exact Alpha.11 tag and release package, pins the known pre-freeze warning set, rejects any new deny-level break, and retains its report.
- The private snapshot ingest now performs a complete second read through the original open handle and requires its length and SHA-256 to match the retained spool. Persistent same-length content drift observed by that pass is detected without relying only on filesystem timestamp granularity; the caller-owned file is not claimed immutable after the reread.
- The README, CLI help, and packaged consumer teach the central rule at the point of use: after admission, consume the `VerifiedArchive` or materialized tree and never reopen the original archive.

## Distribution and dependency boundary

- The release floors remain Ubuntu 24.04 x86_64, macOS 15 arm64, and Windows Server 2022 x86_64. Optimized tests and exact extracted-package checks run natively on each floor.
- Linux additionally ships the authenticated static `sealr-worker` helper and exact manifest. macOS and Windows do not contain the helper.
- Target-specific third-party license bundles cover the combined CLI and verifier graph on every platform plus the production helper on Linux. The verifier introduces no dependency family beyond the CLI graph.
- The source package contract still allowlists only the `sealr` library crate. This GitHub prerelease does not publish another crate to crates.io.
- Rust 1.98 remains the MSRV and exact CI toolchain.

## Important limitations

- Sealr is deliberately narrow and fail closed. It is not a general ZIP, TAR, 7z, package-manager, malware-detection, or process-sandbox replacement.
- ZIP methods 12, 93, and 95; 7z packed headers and LZMA members; LZ4 TAR; RAR4 and RAR5; cpio; ar and deb; RPM; CAB; ISO 9660; UDF; APK signing semantics; and OCI layer semantics are not supported selections.
- Broader GNU TAR and PAX features, including long links, sparse maps, base-256 numbers, ownership, timestamps, vendor keys, and recovery behavior, remain denied.
- The authenticated x86_64 Linux worker accepts only supported ZIP32 semantic records. Structural planning remains in the supervisor, and unsupported profile requests fail before source transfer or effects without in-process fallback.
- Receipts and roots remain unsigned preview identities. There is no authenticated recovery path, complete durability claim, external security audit, stable API or schema freeze, external adopter, or production-readiness assessment.

## What comes next

1. Integrate exact Alpha.12 into one independently maintained publisher, registry, build backend, or installer. The downstream must treat the capability as authority, remove or deny the original archive after admission, and fail when Sealr or evidence verification fails.
2. Move scheduled public API compatibility discovery to the authenticated Alpha.12 package, require an empty warning set, and start its promotion history from zero.
3. Continue measured wheel compatibility and independent trusted-computing-base review while parser breadth stays frozen.
4. Resume the parked 7z LZMA member and packed-header work only after the usefulness, compatibility, and review milestones justify it.
