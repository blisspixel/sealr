# sealr 0.1.0-alpha.11

This eleventh development preview adds one explicitly selected restricted raw POSIX PAX path. It preserves the ZIP32 compatibility default, every earlier policy and identity, strict ZIP64, raw portable ustar, strict gzip-wrapped portable ustar, the supported-preview wheel consumer, and the Alpha.6 reduced-authority Linux boundary. PAX adds no runtime dependency.

It remains a preview. This is not general PAX or TAR compatibility, the default APIs run in process, structural planning is not confined, successful supervised execution remains ZIP32-only on x86_64 Linux with Landlock ABI 3, and this release does not claim production readiness.

## Restricted raw POSIX PAX

- `sealr.profile.tar.pax-portable.v1` is selected only through `ArchiveSelection::TarPax(TarPaxInterpretationProfile::PortableV1)`, `ArchiveFormat::TarPax`, or CLI `--format tar-pax`, and policy v5. Filenames and source contents never widen raw ustar or trigger a retry under another parser.
- The canonical profile digest is `db951f620acf54e67845144e138f9f16994439847a97601e20a424dfea7f4445`. The policy v5 digest is `d1268c72f284f8f1b7ce5e06ada17ef7cbbbc5768a876ee93d103ad21e77d019`.
- Every physical header satisfies the exact portable-ustar checksum, magic, version, fixed-text, numeric, padding, and termination rules. The only added carrier types are local `x` and global `g`.
- An extension contains one or two adjacent canonical records with exact decimal record lengths and complete payload consumption. The only keywords are byte-exact `path` and `size`.
- A fixed four-field state records global path, global size, local path, and local size. Each effective value resolves local, then global, then underlying ustar, and preserves the exact extension and record that supplied it.
- Local state applies to exactly one immediately following ordinary member. Global state persists and replaces only fields named by a later global header.

## Bounds and denied language

- One extension payload is capped at 65,536 bytes, one extension at two records, keyword discovery at 16 bytes, and one archive at 1,024 extension headers. These limits are independent of the policy metadata and ordinary-member caps.
- Effective paths are capped at `min(8191, 256 * max_path_depth - 1)` and still pass the portable UTF-8, NFC, component, reserved-name, collision, traversal, and topology contract.
- Unknown or duplicate keywords, empty values, noncanonical decimal encodings, orphan or chained local headers, timestamp and ownership fields, links, sparse files, devices, FIFOs, GNU carriers, base-256 numbers, mixed dialects, concatenation, recovery parsing, and nonzero hidden padding fail closed.
- Extension carrier names are structural evidence only. They are not destination paths, do not count as files, and cannot be retained, read as members, or materialized.

## Evidence and identity

- PAX uses format-native `sealr.archive-ir.tar-pax.v1` evidence. Ordered extension records bind carrier header, payload, padding, checksum, ranges, raw values, and hashes. Ordinary members bind both underlying and effective names and sizes plus exact provenance.
- A separate covering audit reparses exact ustar framing, canonical PAX records, physical adjacency, padding, terminators, hashes, global and local state, effective values, and provenance before the archive can reach the ready boundary.
- Layout identity uses `sealrTreeV5` with label `sealr.tree.layout.tar-pax.v1`. Redundant overrides or different carrier geometry therefore change layout identity even when the verified output tree is the same.
- Content identity remains format-neutral `sealrTreeV1`. A restricted PAX archive and portable ustar archive may share it only after complete verification.
- The standalone no-Sealr-dependency verifier reconstructs the profile digest, exact source covering, PAX state transitions, provenance, `sealrTreeV5`, and the shared content root from the committed conformance manifest.
- Public conformance tests reconstruct byte-exact controlled outputs from GNU tar 1.35, libarchive 3.8.4 `paxr`, and CPython 3.12.10, then pin their source hashes, ordered records, provenance, layout roots, content roots, and verified payloads.

## Public behavior and effects

- The Rust API and CLI support explicit restricted-PAX inspection and materialization. Retained members and later verified reads use the accepted raw-payload plan without structural reparsing.
- PAX reuses component-bound, no-follow, create-new staging and native no-replace publication on the supported Linux, macOS, and Windows filesystem matrix.
- Selecting PAX with `--worker-manifest` or the supervised Rust API returns typed isolation unavailable before source access, helper launch, stage creation, or fallback. A later semantic record must bind PAX-specific evidence before worker support can exist.
- `apply()` and `--format zip` remain the immutable ZIP32 compatibility path. `tar-ustar`, `tar-gzip-ustar`, `zip64`, and `tar-pax` remain separate explicit selections with matching policies.

## Dependency and assurance boundary

- The shipped library remains at 14 direct runtime dependencies and the pinned cross-platform dependency budgets do not change. PAX uses no general archive framework and no new codec.
- Public tests cover explicit selection, policy authorization, inspection, retention, later reads, materialization, global and local precedence, underlying versus effective evidence, cross-format non-aliasing, malformed records, unsupported features, quotas, and covering drift.
- The independent verifier and production identity tests must agree on the exact profile bytes, PAX IR facts, layout root, and content root. These finite vectors and tests are evidence, not a proof of all inputs.
- Both independent source auditors enforce the inherited portable-ustar zero-size rule for underlying directory headers. Negative and positive controls retain valid nonzero regular-file headers even when PAX changes their effective sizes.
- A dedicated scheduled Linux AddressSanitizer campaign starts from nine digest-pinned deterministic seeds. It exercises accepted ustar subsets, local path and size overrides, global and local precedence, a quota boundary, malformed record length, orphan local state, an unknown keyword, and the extension-size cap. Its pinned 4 MiB input, 600-second campaign, five-second per-input, 1 GiB RSS, and single-job bounds make it reproducible; they do not establish coverage completeness.
- Release promotion requires all seven exact-commit bounded fuzz jobs while preserving one protected `Required CI` authority on `main`.

## What comes next

1. Add a separate raw GNU long-name-only profile using exact GNU magic and one `L` carrier for one following ordinary member. Keep long links, sparse files, base-256 numbers, PAX mixing, and recovery denied.
2. Compose the frozen PAX and GNU raw profiles separately with the existing exact gzip transform. Do not invent wrapper-specific inner semantics.
3. Promote zstd, XZ/LZMA2, and bzip2 one at a time through exact-consumption, memory, checksum, work, license, and minimal-dependency gates.
4. Build a local bounded 7z interpreter with Copy first, then reuse the reviewed LZMA layer. Do not import a full extractor framework.
5. Add cpio, ar/deb, CAB, RPM, and restricted RAR5 through separate threat models and assurance gates. Keep ISO 9660, UDF, and other filesystem images in their own program.

## Important limitations

- The PAX profile accepts only `path` and `size`. General producer output commonly includes timestamps, ownership, charset, vendor, sparse, or link metadata and will be refused unless produced under the documented restricted recipe.
- GNU TAR extensions, gzip-wrapped PAX, zstd, XZ, bzip2, LZ4, 7z, RAR4, RAR5, cpio, ar, deb, RPM, CAB, ISO 9660, UDF, APK signing semantics, and OCI layer semantics remain future separately gated programs.
- The authenticated Linux worker remains ZIP32-only. Stable API and identity review, accumulated assurance history, authenticated recovery, complete durability, external adoption, an external security audit, and a production-readiness assessment remain roadmap gates.
