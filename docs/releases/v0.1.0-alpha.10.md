# sealr 0.1.0-alpha.10

This tenth development preview adds explicit strict ZIP64 and strict single-member gzip-wrapped portable ustar paths. It preserves the ZIP32 compatibility default, every earlier policy and identity vector, the raw portable-ustar profile, the supported-preview wheel consumer, and the Alpha.6 reduced-authority Linux boundary. Both new paths add zero runtime dependencies.

It remains a preview. The default APIs run in process, structural planning is not confined, successful supervised execution remains ZIP32-only on x86_64 Linux with Landlock ABI 3, and this release does not claim general ZIP64, TAR, gzip, process-containment, or production compatibility.

## Strict ZIP64

- `sealr.profile.zip64.strict-ascii.v1` is selected only through `ArchiveSelection::Zip64` and policy v3. Filenames and source contents never widen the ZIP32 default or trigger a retry under another parser.
- The profile accepts one canonical, single-disk, producer-compatible ZIP64 structure with Store or Deflate members and exact ZIP64 sizes and offsets. It denies encryption, links, split disks, unsupported methods, noncanonical width encodings, ambiguous extras, and structural signatures hidden in comments.
- ZIP64 emits format-native `sealr.archive-ir.zip64.v1` evidence and `sealrTreeV3`. The exact covering binds local records, optional data descriptors, central records, EOCD64, its locator, and classic EOCD back to the immutable original source.
- Independent conformance vectors reconstruct the profile digest, semantic ZIP64 evidence, covering geometry, layout roots, and shared content roots without importing Sealr or inflating payloads.

## Strict gzip-wrapped portable ustar

- `sealr.profile.tar-gzip.ustar-portable.v1` is selected only through `ArchiveSelection::TarGzipUstar` and policy v4.
- The wrapper accepts exactly one RFC 1952 member. It validates fixed fields, bounded optional fields, exact FEXTRA subfield framing with unique nonzero identifiers, FHCRC when present, CRC32, ISIZE, exact input consumption, and no trailing bytes or concatenation.
- One bounded immutable decoded TAR becomes snapshot domain one. The exact compressed source remains domain zero. An identity-bound RFC 1952 transform connects them, and the portable-ustar parser validates domain one without reopening or replacing either snapshot.
- `sealrTreeV4` binds the original source, wrapper evidence, transform and decoder-parameter identities, derived TAR digest, inner ustar evidence, and the format-neutral content root. It does not alias raw TAR `sealrTreeV2` even when the decoded TAR bytes are identical.
- Policy v4 independently bounds source bytes, derived bytes, wrapper and archive metadata, file count, member output, aggregate output, path depth, and compression ratio. The separate scheduled ASan fuzz campaign supplies per-input and campaign timeouts; the runtime policy does not claim a wall-clock deadline.

## Public behavior and effects

- The Rust API and CLI support explicit ZIP64 and `tar-gzip-ustar` inspection and materialization. Retained members and later verified reads use the original verified plans without reparsing or redecoding the source.
- Both paths reuse component-bound, no-follow, create-new staging and native no-replace publication on the supported Linux, macOS, and Windows filesystem matrix.
- Selecting either path with the ZIP32-only authenticated Linux worker returns typed `IsolationUnavailable` before source transfer, helper launch, stage creation, or fallback.
- A private non-forgeable authority token now proves that the selected format's covering, member plans, transform graph, integrity checks, and cross-layer audit all passed before any verified archive can reach an effect.

## Independent and adversarial evidence

- The standalone identity verifier independently checks ZIP32, ZIP64, raw ustar, and gzip-wrapped ustar bundles. For gzip-TAR it does not invoke a decompressor; it binds committed derived bytes through CRC32, ISIZE, length, SHA-256, transform identity, complete ustar grammar, and all three relevant tree encodings.
- The gzip-TAR bundle contains two source-distinct canonical encodings of one TAR and proves different `sealrTreeV4` roots, one shared raw-TAR `sealrTreeV2`, and one shared `sealrTreeV1` content root.
- A dedicated scheduled Ubuntu AddressSanitizer campaign starts from 44 reproducible digest-pinned seeds. It covers stored, fixed, and dynamic Deflate, every supported optional field, malformed framing, integrity failures, two-member and three-member concatenation, trailing input, hostile ustar, and every public quota axis.
- Strict ZIP64 has its own public planning fuzz target and independent mutation controls. Release promotion requires exact-commit success for all six bounded fuzz jobs without adding another required main branch check.
- The repository pins exact normal and build dependency closures for Linux, macOS, and Windows. ZIP64 and gzip-TAR add no package. Future codecs have a default maximum of two promoted runtime packages and deny native toolchain links unless separately approved.

## Distribution and verification

- Only the `sealr` library crate is allowlisted for crates.io publication. Required CI verifies the extracted crate, native CLI packages, exact file contracts, dependency budgets, third-party license closure, and all public format paths on Linux, macOS, and Windows.
- The tag workflow produces exactly the Linux x86_64, macOS arm64, and Windows x64 native archives plus `SHA256SUMS` and GitHub build-provenance attestations. It stages an exact prerelease draft and never publishes it.
- Trusted local promotion requires the exact protected `main` commit, the single stable `Required CI` check, all six exact-commit scheduled fuzz jobs, release immutability, draft and asset readback, checksums, and provenance before changing only the draft and prerelease fields.

## Important limitations

- `apply()` remains the strict ZIP32 compatibility facade. ZIP64, raw ustar, and gzip-wrapped ustar require explicit selections and matching policies.
- ZIP64 is intentionally narrower than general ZIP64. It does not support split disks, encryption, links, arbitrary extras, broad methods, or recovery parsing.
- Gzip-TAR accepts one strict gzip member containing one portable ustar archive. PAX, GNU extensions, bzip2, XZ, zstd, concatenated gzip, sparse files, links, special files, and recovery behavior remain unsupported.
- 7z, RAR4, RAR5, cpio, ar, deb, RPM, CAB, ISO 9660, UDF, APK signing semantics, and OCI layer semantics remain future separately gated programs.
- The authenticated Linux worker remains ZIP32-only. Stable API and identity review, accumulated assurance history, authenticated recovery, complete durability, external adoption, and an external security audit remain roadmap gates.
